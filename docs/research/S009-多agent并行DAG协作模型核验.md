# S009:多 agent 并行 DAG 协作模型核验

> 问题:多 agent 靠 DAG 义务图、检索复用与免冲突设计协作的心智模型是否站得住,哪些纪律值得吸收进 herdr 飞轮。方法:Notion 核验笔记全文抓取(2026-09-17);笔记依据 Anthropic FLT 形式化原帖、Prove2Me DAG 技术说明书(笔记对一手材料核对 2026-09-05)与官方 workspace SKILL.md。结论:四则飞轮已有等价,五则真新增(第七十八批吸收进 herdr-flywheel),余下留档。

## 模型十二则

以下转录自核验笔记,断言态统一 [经验: Notion 核验笔记 2026-09-17 全文抓取,笔记一手核对 2026-09-05],不逐则重复标。

### 编排核心

- 义务图:图上只存「还欠哪些证明」,不存「谁在干活」;agent 每次按需拉取自己那条依赖链的局部信息,并在每轮结束重读状态,避免依据启动时的过期图工作
- proof-sketch 条件归约:上层不必等下层证完,可以先提交并验证「只要 A、B 成立,G 就成立」的连接证明;连接正确性与子结果正确性拆开,父任务先接线后兑现,这是上下层真正并行的关键
- 推论:「父文件没有 sorry」不等于「依赖闭包没有 sorry」;本地编译通过不能代替全图义务检查

### 容错与一致性

- 租约加心跳:worker 崩溃后租约到期,任务可被重新领取;已保存的证据与失败记录不随 worker 消失
- 任务与尝试分开记录:不为「避免冲突」禁止多路线尝试,把任务与尝试分开记即可
- 提交幂等:同一请求重试不应产生互相矛盾的提交;同一幂等键携带不同内容应被拒绝;旧版本产物可存档但不得覆盖新版本的完成状态
- 依赖变化必须重评估:上游变了,要么已有兼容证据可复用,要么重跑部分验证,要么重写;不能只改图上的链接却沿用旧验证结果
- deprecated 不等于作废证明:废弃只是发现/展示层标记;依赖变化的正确处理是重评估与重提交,两件事在该系统里被明确区分

### 验收与度量

- 验证器独立于生成者:实现者不应有权修改验收条件,否则可以靠删测试、降目标、缩范围来「完成」
- 产量不是完成证据:agent 数、生成行数、讨论条数只描述规模;该次运行消耗约 60 亿 output token,不该被解读为「近乎零成本」
- 理想下界(技术说明书给出的分析模型,非实测公式):加 agent 不能突破依赖关键路径;扩容前先判断瓶颈是「独立任务不够」「验证资源不够」还是「接口频繁变化导致返工」

### 能力边界

- 检索不是语义/向量召回,公开实现是子串匹配加过滤;把「可检索」当成「有向量库」会高估能力

## 与 herdr 飞轮对照分流

已有等价(不重复吸收,引 SKILL.md 现行纪律):

| 模型则 | 飞轮现行等价 |
| --- | --- |
| 验证器独立于生成者 | 断言节:总台逐项独立复核,不采信口头补述 |
| 产量不是完成证据 | 回执节:对方陈述不作数,sha/门禁/CI 自取 |
| 提交幂等的甄别面 | 回执节:插队回执以 commit sha 加 diff 范围甄别 |
| 依赖变化处理的雏形 | 吸收节:每轮反馈当场分流 |

真新增(第七十八批吸收进 SKILL.md「并行派单与义务图」节与 references/parallel.md):义务图台账、条件归约先接线(含闭包清账推论)、租约与改派、任务与尝试分开记(含完成态幂等)、依赖变化必重评估、扩容前瓶颈三判。

留档不吸收:deprecated 与重评估的两事区分(该系统发现层特有);检索为子串匹配非向量(该系统实现细节,飞轮无此面);60 亿 token 产量数字(背景量级,无操作含义)。
