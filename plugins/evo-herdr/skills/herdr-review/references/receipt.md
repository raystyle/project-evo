# 回执与轮次

> 三态回执、逐条对照、轮次到终审放行。实证自 D46 至 D53 回执原文与五轮复核链。

## 一、三态

| 态 | 语义 | 形态 |
| --- | --- | --- |
| CONFIRM | 干净,放行 | 「CONFIRM 收讫」加放行动作(推 main、CI run id) |
| F#(必修) | 缺陷,须修 | 编号 + 证据(行号、机制、复现路径)+ 为什么是缺陷 |
| G#(建议) | 好实践、文档面 | 编号 + 建议;工位自行采纳或记档给理由 |

## 二、回执句式(工位修完回评审方)

```text
D46 对线回执(codex):F1 与 G1-G5 全修并入原批已推,CI 四岗绿,谢复核。
- H1/F1(双线必修):build.yml asset 补 .exe;seed.py _TRIPLES 切 gnu 名,...(逐条对照)
- G2:official_asset_meta 单拉 release,asset_in_release 拆分本地按名序匹配。
```

- 编号对齐评审方的 F/G 序号,逐条给修复落点;终态证据(CI run id、测试计数)收尾
- **采纳纪律**:评审方的实证被采纳时点名(「你的 NU1510 与 A/B 零字节差实证采纳」);不采纳的给理由(成本、YAGNI、口径一致),记档不做

## 三、轮次

```text
评审回执(F/G)
到 修订落实回执(F/G 全修,两提交待终审)
到 评审方二轮快核(只核修复增量,不复读全量)
到 终审放行(「请快核后我推 main」「CONFIRM 收讫,推 main 后 CI run ... success」)
```

- 修复本身也要过复核:一轮修复引入或掩盖的缺陷由二轮抓出(实证:一轮 settle 自动化后被二轮抓出四个真缺陷),全修不免二轮
- 达成一致前不推 main;评审会话 idle 才收件,blocked 是等人裁,问用户不代答
- 快核请求要点名核什么(「五提交待终审,git log --oneline -6 请快核后我推 fork main」)
