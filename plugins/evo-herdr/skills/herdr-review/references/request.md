# 评审请求

> 五件结构,全部实证自 hst_rs 系工位 D46 至 D53 请求原文。接收方(评审会话)没有派发方的上下文,请求必须自包含到逐条可对账。

## 一、五件结构

### 1. 标题句(编号 + 门禁语句 + 批面)

- 单笔形:「review 请求(D47,对齐后我方才推 main)」「D46 对线 review 请求(推送前门禁,规则 8),两提交待推 main」
- 交付批形:「hst_rs 交付批评审请(七笔未推 main,基线 2421964,仓库 /mnt/wsl/repos/hst_rs)」
- 要素:讨论编号或批次背景一句、笔数与基线 sha、仓库路径、门禁语句(对齐后才推 main / 达成一致前不推 main)

### 2. 提交面

- 小批:逐笔 `git log --oneline` 清单,每笔一句主题
- 单笔:「请复核本仓 HEAD 提交(git show <sha>)」:给 sha,让评审方自取 diff,不粘贴大段补丁

### 3. 改动面逐条枚举

编号列文件与语义,评审方按条对账:

```text
改动面:1) dev-release.yml 的 windows-latest msvc 岗换 ubuntu-latest 交叉岗(...);2) src/update.rs
host_asset_name windows 臂改 pc-windows-gnu.zip(...)
```

### 4. 背景与已验证据

- 为何改:用户裁定日、上游实证、宿主报修来源
- 已验面:本机测试结论、CI run id、A/B 实证:评审方不复验已验面,专看增量与漏项

### 5. 明确指令(分级用词)

- 全量:「请逐行核 diff 并回执」「通读找 bug」
- 快核:「请快核」「请核三态边界(... 的语义对 MSI 型是否安全重复装)」:点名要核的边界,不撒网

## 二、纪律

- 不带基线的「帮我看看」不算评审请求;无门禁语句的随手 review 不进门禁
- 已验面不转嫁复验(写清已跑什么);改动面漏条=评审盲区,枚举到文件级
- 大规模全量 review 不走会话直发,走任务协议(委派即产物,见 findings.md)
