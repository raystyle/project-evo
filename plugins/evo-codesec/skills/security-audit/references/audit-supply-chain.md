# 供应链与发布专题审计

> 本篇角色：目标解析依赖、从不可信贡献构建、运行 CI、产出发布产物、签名或晋升构建、加载插件或更新已部署软件时，审计从源码与依赖到用户所运行产物之间的信任交接。

#### 何时使用本篇

目标解析依赖、从不可信贡献构建、运行 CI、创建发布产物、签名或晋升构建、加载插件或更新已部署软件时使用本篇。覆盖从源码与依赖到用户所运行产物的信任交接。本地二进制加载器内部缺陷用 `audit-memory-binary.md`，运行时工作负载权限用 `audit-cloud-deploy.md`。

大型目标按依赖解析、CI 隔离、产物来源（provenance）、发布授权、更新器/插件信任拆分。

## 核心纪律（加入本领域每个 agent 提示词）

```
- 可变或已知易受攻击的依赖本身不是发现。要展示谁能影响解析、哪个构建消费它，以及其后是什么执行或发布边界。
- 完整追踪每次交接的完整性：源码身份、解析出的输入、构建 worker、产物身份、测试结果、签名/attestation、晋升与更新消费者。
- CI 配置就是授权代码。确立哪个事件触发 workflow、谁的代码在跑、存在哪些密钥与令牌，以及它可发布或改动什么。
- 与产物取自同一不可信位置的校验和不构成独立完整性。识别可信根与失败行为。
- 仓库内控制流缺陷加有界本地验证用 `confirmed`；不可观察的分支保护、托管 runner、registry、签名服务或生产晋升事实用 `needs_validation`。
```

## 依赖与构建输入攻击类（subagent_type: `general`）

**依赖源与命名空间混淆**
解析器配置可能选中意外的公共/私有命名空间、回退 registry、镜像源、仓库或源 URL。审查包名、源优先级、lockfile 与校验和使用、备用构建文件、平台特定解析，以及首次安装与更新行为的差异。

**可变与未固定的构建输入**
构建消费分支、tag、未验证的 submodule、下载的工具、生成的资产、远程 include、浮动版本的 CI action 或内容可变且未经源码评审的容器 tag。要求存在更低信任的写入者，以及进入可信构建产物的路径；可复现性本身不证明真实性。

**生成源码与 codegen 来源缺口**
schema、vendored 归档、生成的客户端、本地化、文档示例或二进制 blob 产出可执行或随包发布内容，却没有与源码相同的评审与完整性闸门。对比本地重新生成与已提交产物，验证谁控制输入与生成器。

**构建上下文包含**
密钥、本地配置、仓库元数据、测试 fixture 或开发者产物因构建上下文与 ignore 规则超出预期发布输入而进入包或镜像。确认最终产物确实暴露真实凭据、私有数据或特权配置。

## CI 与自动化攻击类（subagent_type: `general`）

**特权 workflow 中的不可信代码**
pull request、issue 评论、fork、依赖更新或外部事件以贡献者可控代码运行，且带有受保护密钥、写令牌、部署权限或可信 runner。对比触发类型、checkout ref、审批闸门、环境保护与权限收窄。不要假设源码中不存在的仓库托管默认值。

**workflow 命令与表达式混淆**
攻击者可控的分支名、commit message、issue 字段、artifact 名、matrix 值或生成输出未经规范化校验，进入 shell 命令、模板表达式、路径或特权 workflow 输入。

**缓存、artifact 与工作区信任混用**
更低信任的任务可以填充缓存、artifact、共享工作区或输出，更高信任的任务随后恢复并执行或发布它。审查缓存键与命名空间、artifact 生产者身份、digest 绑定、保留策略，以及晋升是否按可变名称重新解析。

**自动化身份越权**
CI 任务获得的权限超出操作、仓库、环境或时长所需，且不可信任务输入可选择受影响资源。仅缺最小权限属加固；要求存在可触达的特权操作。

## 发布与更新攻击类（subagent_type: `general`）

**构建到晋升的替换**
测试、评审、签名与发布引用可变 tag、文件名、channel 或 artifact ID，而不是同一个不可变 digest。检查构建与发布之间的每次复制、重打包、架构合并与 provenance 步骤。

**发布授权与签名策略缺口**
发布或签名被来自错误 workflow、仓库、分支、环境、密钥角色或阈值的一方接受。审查 attestation 内的身份声明，并验证消费者确实校验它们，而不只是一个有效签名。策略要求处，轮换、过期与吊销必须 fail closed。

**更新元数据与回滚混淆**
更新器认证了载荷字节，却没有认证版本、产品、平台、channel、目标路径、过期或回滚状态；或它接受了来自不同授权事务的元数据与载荷。验证原子安装与恢复行为。没有策略绑定的签名 API 调用是不完整的。

**插件与扩展信任扩张**
扩展包获得超出其声明范围的主机权限；更低信任的发布者可以替换另一发布者的身份；或安装/更新 hook 在真实性与能力检查之前运行。有意安装任意同用户插件不构成特权边界。

## 通用手法（贯穿上述各类）

- 从已发布 digest 或已安装更新反向走向每个源码、生成输入、凭据、worker、缓存、测试结果与授权决策。
- 并排对比不可信与受保护的 workflow 事件。标记两者之间每个持久化通道跨越，并要求不可变身份加生产者信任。
- 审查吊销密钥、下载失败、缺失 attestation、部分平台发布、回滚与 registry 故障路径。失败策略是发布完整性的一部分。

## 验证规则（报告本篇任何发现前适用）

1. 指明更低信任的参与者、可控的源码/缓存/artifact/元数据、消费它的可信任务或更新器，以及导致的未授权发布、代码引入、密钥泄露或特权执行。
2. 跨被破坏的交接证明产物身份。不同的可变名称或未绑定 digest 必须到达真实消费者。
3. 在固定版本上核实包管理器、仓库托管方、registry 与签名的内建默认值。托管侧未知的控制点要求 `needs_validation`。
4. 本地验证保持有界：使用无害 fixture 仓库、哑凭据标记、本地 registry/配置与非生产 artifact 命名空间。不要发布或改动真实发布。
5. 只有完整的源码可见交接加有意义结果才返回 `confirmed`；否则返回 `needs_validation`，并写明所有者必须观察的确切分支、runner、registry、签名或部署事实。
