# 协议、RPC 与消息专题审计

> 本篇角色：目标系统使用 gRPC、GraphQL 传输、Cap'n Proto、Thrift、Protobuf、自定义二进制协议、流式 RPC、webhook、broker、队列、pub/sub 或事件总线时，审计对端身份、消息的逻辑解释、路由、重放、顺序与投递语义。

#### 何时使用本篇

目标使用 gRPC、GraphQL 传输、Cap'n Proto、Thrift、Protobuf、自定义二进制协议、流式 RPC、webhook、broker、队列、pub/sub 或事件总线时使用本篇。覆盖对端身份、消息的逻辑解释、路由、重放、顺序与投递语义。解析器内存安全用 `audit-memory-binary.md`，HTTP 分帧用 `audit-web-auth.md`，可用性影响用 `audit-resource-exhaustion.md`。

大型系统按生产者/消费者对、外部/内部对端角色、同步 RPC、流式与异步消息路径拆分。

## 核心纪律（加入本领域每个 agent 提示词）

```
- 「internal（内部）」不是认证。在每一跳指明对端身份，并展示它如何成为用于授权的应用 principal。
- schema 校验只证明消息形状，不证明来源、资源权限、顺序或取值安全。把解码后的字段追到策略与副作用。
- broker 保证与应用保证不同。评估状态变更前，先写清重试、顺序、确认（acknowledgement）、去重与事务行为。
- 主张解析分歧需要两个具体消费者、schema 版本或线上表示（wire representation），以及一个安全相关的分歧值。
- 源码完整路径加有界的本地生产者/消费者测试用 `confirmed`；仓库外的 broker ACL、服务网格身份、topic 挂载或兼容性行为用 `needs_validation`。
```

## 分帧、schema 与解释攻击类（subagent_type: `general`）

**消息边界与规范化分歧**
组件在长度、压缩、重复字段、未知字段、编码、数值宽度、归一化或信封/正文优先级上不一致。对比生成解析器与手写解析器、网关、语言绑定与版本转换器。确认解码后哪个 principal、资源或操作产生了差异。

**联合类型、枚举与默认值混淆**
未知变体、缺失判别符、零值、默认权限或兼容性映射进入假设「已验证分支」的代码。审查穷举分发、default 分支，以及旧消费者如何解读新增字段。

**信封与载荷身份错配**
授权使用看似可信的路由或信封元数据，而 handler 实际作用于正文中冲突的租户、账户、subject、对象或发送方。判定哪个来源是权威，并确保客户端无法覆盖它。

## RPC 身份与授权攻击类（subagent_type: `general`）

**拦截器与方法路径不一致**
authn/authz 拦截器覆盖 unary 方法，却漏掉流、reflection、health、网关转码路径、兼容服务或单条流消息。把每个注册与路由对比到同一操作。

**对端身份与应用 principal 混淆**
mTLS、工作负载身份、bearer 元数据、转发身份或 broker 凭据认证的是通道，但调用方可控字段却选定用户或租户。通道身份与所声称 principal 之间必须有确定性策略绑定。

**逐项与流式授权缺口**
一条流、订阅、批量或汇总消息只授权一次，随后条目指向不同资源，或在角色、成员资格或令牌吊销后仍继续。复查 scope 可能变化的位置，并把订阅绑定回其原始 principal。

**回调与应答关联混淆**
可预测、复用或跨租户的 correlation ID 让某个响应、webhook、取消或确认满足了另一个调用方的未决操作。把每个未决请求绑定到已认证对端、租户、操作与生命周期。

## broker 与队列隔离攻击类（subagent_type: `general`）

**topic、routing key 与订阅范围缺口**
发布者或订阅者可以选定另一租户的 topic、通配符、consumer group、分区、应答队列或死信路由。在可见处检查 broker 强制的 ACL，以及应用侧的命名空间拼接。载荷里的租户文本不构成隔离。

**死信、重试与诊断信息泄露**
路由到死信队列、错误 topic、追踪或运维视图的消息含有更低信任消费者可读的密钥或跨租户载荷。在失败路径上审查策略与脱敏，而不只是正常投递。

**不可信生产者被当作控制平面**
消息体可以自称为 admin 事件、provider 回调、复制记录或迁移指令，却没有经过独立认证的生产者与事件类型。在进入特权处理前验证签名与 source/account/audience 绑定。

## 重放、顺序与事务攻击类（subagent_type: `general`）

**重复投递与幂等缺口**
重试或重复投递重复触发副作用，因为缺少去重、去重发生在变更之后，或所用键跨租户/操作冲突。确认 broker 的投递模型，以及那个并非天然幂等的副作用。

**乱序与陈旧消息被接受**
更旧的状态、已吊销的成员资格、已取消的任务或提权前的授权在新状态之后到达并覆盖它。审查序号/版本检查、墓碑（tombstone）、分区变更与恢复/重放流程。

**确认/提交顺序缺陷**
确认发生在持久提交之前并丢失安全相关的工作；或提交发生在不可靠确认之前并复制一次变更。评估事务性 outbox/inbox 行为与失败恢复。

**部分多消费者转换**
多个消费者共同实现一个授权或业务转换，但重试与部分失败导致只有子集提交。识别必须原子持久化的不变量，或以当前授权进行补偿。

## 通用手法（贯穿上述各类）

- 为每个消息家族画出 `producer -> broker/transport -> gateway -> consumer -> storage` 链路。在每一跳记录已认证对端、权威租户/资源字段、校验与副作用。
- 把同一份小 fixture 喂给仓内每个 schema 版本或语言绑定。测试重复、缺失、未知、边界、重放与乱序消息，不制造负载。
- 对比正常、重试、死信、重放、迁移、reflection、流式与网关转码路由。安全策略必须在传输变化后仍然成立。

## 验证规则（报告本篇任何发现前适用）

1. 指明真实的生产者或对端、被接受的消息、已认证通道身份、受影响 principal/资源，以及未授权变更或泄露。
2. 主张解析分歧时，引用双方解析器/消费者与分歧的解码值。任一侧安全拒绝都会阻止确认。
3. 主张重放/顺序问题时，确立实际投递保证，并用有界的本地/内存传输复现不变量破坏。
4. 授权与隔离问题要验证源码可见的全部拦截器、broker ACL、网关与消费者层。外部挂载使候选发现降为 `needs_validation`。
5. 只有完整的消息生命周期加观察到的有意义结果才返回 `confirmed`；否则返回 `needs_validation`，并写明所需的确切 broker、服务身份、路由或投递事实。
